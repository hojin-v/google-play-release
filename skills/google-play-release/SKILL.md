# Google Play release

Read this project's release config and [workflow](references/workflow.md). Keep app identities, decisions, test scenarios and UI/security rules in that app's `play/`/`docs/`; use the shared toolkit for execution and receipts.

## Release intent and production gate

- Default to local preparation and a reviewable test candidate. A generic “deploy/upload/update”, a successful test, a request to push Git, or authorization for an earlier release/app is **not** production authorization. An explicitly authorized internal draft may be uploaded; a draft is not tester delivery or policy approval.
- Before production, show the concrete app/package, version/code, AAB hash, track, rollout, tested device/OS coverage and any remaining failures. Complete authorized preparation first. Ask which release scope the user intends if production was not explicitly authorized for this current work. If the current task already has clear production authorization, reuse it without asking again.
- Never treat unit tests, emulator results, or a different sideload/debug package as proof of actual Play-variant/device compatibility. `prepare` writes a build proof and a pending `review-<hash>.json`; complete each app's required physical-device observations with actual device, OS/SDK, installation, matching APK reference and evidence. Do not mark an unperformed check passed or silently remove/waive a failing requirement. Test the matching Play APK/AAB; Play internal testing is available when the installed Play signature prevents a local update. Never delete real app data or bypass security to make a test pass.
- If the user explicitly accepts completed physical APK validation and instructs you to omit additional Play-file testing, honor that scope without repeating the question. Record `accepted_prior_validation`, the actual prior package/version/APK hash, device/OS and evidence, plus `user_acceptance` with `source:user`, the actual request and coverage limitation. Never call this a current-file pass, infer acceptance from a generic release request, accept a previously failed test, or erase device/SDK constraints. The exception stays bound to this release and its approval.
- Only after required checks pass and explicit current-scope production authorization exists, run `approve` with the user's actual request and the requested rollout. It records that authorization; the command itself does not obtain user permission. Do not manufacture approval from ambiguous text or auto-create it because `release` was blocked. Approval/evidence are bound to package, version, AAB/APK, metadata/config and rollout. Changed artifacts require renewed review of the changed result; existing applicable authorization can be reused under its scope.
- `release`, production `promote`, and production `resume` require `approval:` and `evidence:`. Reuse the tested AAB; CI production downloads the specified preparation run instead of rebuilding. These gates catch missing/stale records, not every bug or forged operator statement. GitHub required-reviewer protection is an additional account-dependent control, not assumed to be configured.
- Internal `draft` leaves production binaries, shared listing/images and app contact unchanged. `sync_listing` changes the shared store listing and requires `acknowledge_shared_listing:true`; never use it as a harmless test-only operation. Do not silently drop Google's automatic-review hold. If Google requires automatic review, retain the edit and explain the actual operation before using explicitly authorized `automatic_review:true`.

## Workflow

1. Identify the exact toolkit commit used locally and the app workflow's pinned revision. Compare with the upstream branch before diagnosing a missing shared feature; do not assume the local checkout or a caller's old pin contains recent fixes. Preserve local changes and other apps' upstream work when updating; never force-push over them. Run `bin/play-release --project <app> doctor`; start a new config from `examples/release.json` when missing. Inspect repo instructions, variants, permissions/SDKs/data flows, signing continuity and current official requirements. Do not copy another app's facts or credentials. Use app-specific `artifact_checks` for additional shipped-artifact validation.
2. Run `bin/play-declarations --project <app> questions --json`. Reuse this app's verified user/Console facts; ask only unresolved business/service choices through the available user-input tool, in small batches. Save answers with actual `user|code|console` provenance. Unknown facts remain pending. These records do not submit Console forms or establish IARC/policy approval.
3. With available credentials, use read-only `verify_access` and `status` even if local bootstrap is false. Diagnose actual API readiness/errors before delegating setup to the owner; the flag alone is not an API restriction. Mutations warn on unconfirmed bootstrap but do not mark it complete. Establish credentials and public identity/URLs. Ask for credential paths, never secret values. First publication still requires app creation, a manual first AAB save if the actual API reports it is needed, App Signing decisions and Console declarations/testing eligibility; preparing an AAB does not choose the Google-held signing key. Explain an irreversible signing choice before it is made.
4. Inspect current imagery after UI changes. Prefer actual device captures; reuse an explicit user preference for HTML previews. Configure app-owned `screenshot_config`, generate and inspect every image; keep dimensions/order/hashes and label illustrative system UI. Browser/native renders are not device test evidence. `prepare` generates previews and runs configured Gradle tests/lint/build plus artifact checks. `check --aab ... --store` audits the exact candidate.
5. Complete the physical test review, then obtain/record applicable production intent as above. Use `draft` for an internal test draft; do not mistake it for a completed test. Use `release` for a validated new production AAB plus listing in one edit, or `promote` with an explicit `to:` for an already uploaded identical AAB. Never default to 100% rollout.
6. Shared local/CI mutation lanes now save `remote-before.json`, `remote-after.json`, and `submission-receipt.json`. They verify version/AAB, image order/hashes, country preservation, and test/production separation. A failed/unavailable verification is not success. API `completed` is not Google approval or public availability; report those separately.
7. On error, read `status`, preserve the edit receipt and the same AAB, and do not blindly reupload. `resume` validates the approved artifact/scope and staged changes before retrying only commit. `resume track:internal` may resume an original internal draft, preserving its production/listing baseline; explicit automatic-review authorization is still required when Google rejects the hold. An expired/deleted edit must be established before opening a replacement. Do not cancel an in-progress review on your own.

Generated artifacts and operator approval/evidence belong under the app's ignored build directory or an explicitly selected private review record. Secrets stay outside Git. The toolkit's technical checks are not malware scans, policy approvals or a guarantee across all manufacturer firmware.

For a new app whose API permits only draft releases, `promote aab:<same-file> version_code:NN from:internal to:production release_status:draft` (omit rollout) saves only a production draft. It does not publish or authorize a later rollout. The production-delivery approval gate applies when moving beyond draft. A draft resumption must match the original saved draft receipt and stage. Keep country intent `ALL_AVAILABLE` separate from actual Console country codes; verify actual availability instead of inventing codes. Remote snapshots retain actual localized release notes.
