# 다른 앱 재사용성과 정식 출시 경계 점검 — 2026-11-15

Shit의 빠른 배포에는 공통 도구 외에도 미리 준비된 앱별 설정·콘텐츠 선언·비공개 서명/서비스 계정 경로·로컬 Ruby·기기 연결과 수동 대조 작업이 있었다. 또한 작업 당시 로컬 도구는 603d31f에 머물러 있었고 원격에는 최초 업로드 준비 확인·API 오류·프로덕션 초안·국가 선택·RELRO 검사 수정이 이미 추가돼 있었다. 이 원격 수정들을 보존해 통합했다. 다른 앱의 실제 실패 로그는 제공되지 않았으므로 그 앱의 개별 실패 원인을 확정하지 않는다. 아래는 저장소 비교로 확인한 공통 구조의 누락과 수정이다.

| 기존 차이 | 공통 도구에 반영한 처리 |
| --- | --- |
| 로컬 도구·앱의 고정 리비전과 최신 원격이 다를 수 있음 | 작업 시작 시 실제 도구 커밋·워크플로 고정 리비전·원격 비교. 기존 변경과 다른 앱의 수정을 보존 |
| 새 앱에 필요한 설정·환경이 없으면 짧은 오류로 중단 | 다른 앱용 구성 예시와 계정 접근 없는 doctor 진단 |
| CI JDK 17, 특정 앱에 쓰인 NDK/CMake를 기본 설치 | 앱별 java_version/android_sdk_packages 사용 |
| APK 보안 검사는 Shit에서 따로 명령 실행 | 공통 artifact_checks 훅. 해당 앱의 실제 검사 규칙은 앱 소유 |
| 단위 테스트/서명 검사만으로 release 명령 실행 가능 | 빌드 증거 + 기기/SDK/설치/결과 + artifact-bound 정식 승인 요구 |
| 오래된 공기계 결과만 있어도 최신 기기 호환 누락을 막지 못함 | 앱별 시나리오의 min_sdk/max_sdk/device_pattern 검증 |
| 프로덕션 CI가 테스트 후 재빌드 | 준비한 run ID의 동일 파일을 내려받아 제출 |
| 로컬 원격 전후 대조·제출 기록을 수동 Python으로 처리 | 모든 로컬/CI mutation lane에서 전후 조회·해시/순서/국가/트랙 대조·영수증 저장 |
| 내부 업로드에 스토어 문구/이미지/문의도 포함 | 내부 draft에서는 공용 스토어 정보 제외, sync_listing은 공유 범위 명시 필요 |
| Google이 review-hold를 거부하면 자동으로 옵션 생략 | 기본 중단/기존 edit 유지. 적용 범위에 대한 명시적 허용이 있을 때만 같은 edit 재시도 |

사진 촬영 여부, 카메라 발신자 신뢰, ADB/OS 동작, HTML UI와 개인정보처리방침 본문은 해당 앱의 기능이다. 이들을 공통 도구로 복사하지 않는다. 계정 자격증명도 공통 코드에 포함하지 않는다. bootstrap 플래그만으로 API를 막지 않고 verify_access/status로 실제 준비 상태를 확인한다. API가 요구하는 첫 업로드·앱 생성·서명 선택·정책 설문·테스트 자격은 해당 계정에서 확인한다. 프로덕션 draft 저장과 실제 사용자 배포는 구분하고 draft 이후 출시에는 별도 승인·검증을 요구한다.

정식 승인은 단순 “배포”, Git push 요청, “테스트 잘 된다”에서 추정하지 않는다. 현재 파일과 검증 결과를 먼저 준비하고 정식 범위가 불명확할 때만 확인한다. 이미 명시적으로 요청한 현재 정식 작업은 같은 허가를 재질문하지 않고 기록한다.

자동화 테스트는 두 번째 가상 앱(com.example.other)에서 공통성, 누락/다른 앱/변경 파일/배포 비율/기기 범위/실기기 결과 미작성의 차단을 확인한다. Publisher는 가짜 응답으로 검사하며 실제 Google 업로드를 사용하지 않는다. 추가로 Shit의 기존 AAB/APK에서 코드 일치·앱별 artifact_checks와 doctor, 자격증명 접근 전에 정식 명령이 거부되는 경로를 검사한다. 실제 새 앱의 출시나 GitHub required-reviewer 운영 설정을 완료했다는 의미는 아니다.
